# 08. 감사 로그(변경 이력) 설계안 (승인 대기)

> 작성일: 2026-10-16 · 관련: [01-analysis.md](01-analysis.md) C7, [05-remaining-issues.md](05-remaining-issues.md) O5
> **이 문서는 설계안이다. 승인 전에는 코드·DB를 바꾸지 않는다.**

## 1. 목적

"누가, 언제, 무엇을, 어떻게 바꿨는가"를 나중에 확인할 수 있게 한다. 특히 다음 질문에 답할 수 있어야 한다.

- 이 거래처의 미수금이 왜 이 금액이 됐나? (최근 실제로 겪은 문제)
- 이 매입매출·입출금 내역을 누가 고치거나 지웠나?
- 이 직원의 권한(메뉴 권한·역할)을 누가 언제 바꿨나?
- 누가 비밀번호를 초기화했나, 로그인 실패가 반복된 적이 있나?

지금은 결재 단계(`approval_steps`)에만 결정 기록이 남고, 나머지는 서버 로그(콘솔)뿐이라 지나간 일을 추적할 수 없다.

## 2. 무엇을 기록할지 (범위)

전부 기록하면 소음이 많아진다. **돈·권한·삭제**에 집중한다.

| 대상 | 기록하는 일 | 남기는 내용 |
|---|---|---|
| 매입매출(`transactions`) | 등록·수정·삭제 | 바뀐 필드의 전/후 값(금액, 거래처, 결제 상태, 남은 금액 등) |
| 입출금(`payments`) | 등록·수정·삭제 | 바뀐 필드의 전/후 값 |
| 거래처(`clients`) | 등록·수정·삭제, **미수금/미지급금 잔액 변화**, 계좌 정보 변경 | 잔액은 어떤 요청 때문에 바뀌었는지(입출금 등록, 매입매출 수정 등)까지 |
| 직원 계정(`users`) | 등록·수정·활성/비활성, 역할·직책·메뉴 권한 변경, 비밀번호 초기화 | 권한 전/후. **비밀번호 값은 남기지 않고 "변경됨"만** |
| 문서(`project_documents`, `proposals`) | 삭제, 결재 상태 변경(승인·반려·삭제 결재) | 상태 전/후 |
| 로그인 | 성공·실패·시도 제한으로 차단 | 이메일, 접속 주소 |

기록하지 않는 것: 조회, 일정·메모(할 일)·공지 같은 일상 기능, 출퇴근 기록(이미 그 자체가 기록이다), 파일 내용.

## 3. 저장 구조 (새 테이블 1개)

`audit_logs`

| 컬럼 | 내용 |
|---|---|
| `id` | 번호 |
| `created_at` | 시각 |
| `user_id`, `user_name` | 누가(이름은 당시 이름을 함께 저장해 계정이 지워져도 읽을 수 있게) |
| `ip` | 접속 주소 |
| `request` | 어떤 요청이었는지 (예: `POST /api/payments`) |
| `action` | `create` / `update` / `delete` / `login_success` / `login_failed` / `login_blocked` 등 |
| `entity_type`, `entity_id` | 무엇을 (예: `client`, 7) |
| `changes` | 바뀐 필드의 `{필드: [전, 후]}` (JSON) |
| `summary` | 사람이 읽는 한 줄 설명 (예: "크레신 미지급금 550,000 → 50,000") |

인덱스: `(entity_type, entity_id)`, `created_at`, `user_id`. 5인 규모에서 하루 수십~수백 건이라 용량 문제는 없다(1년 수 MB 수준).

Alembic 리비전 `0003_audit_logs`로 추가한다(07 문서의 절차: 백업 → upgrade).

## 4. 기록 방식

| 방식 | 장점 | 단점 |
|---|---|---|
| A. 각 API에서 직접 기록 함수 호출 | 기록 시점·내용을 정확히 고를 수 있다 | 호출을 빠뜨리기 쉽다. 잔액처럼 **여러 곳에서 간접적으로 바뀌는 값은 놓친다** |
| B. DB 변경 감지(SQLAlchemy 이벤트)로 자동 기록 | 대상 테이블의 변경은 빠짐없이 남는다. 잔액이 입출금·매입매출 어디서 바뀌든 잡힌다 | "누가"를 알려면 요청 정보를 따로 전달해야 한다 |

**제안: B를 기본으로 하고, 로그인처럼 DB 변경이 없는 일만 A로 기록한다.**

- 요청마다 "현재 사용자·접속 주소·요청 경로"를 요청 범위 변수(`contextvars`)에 담는다(인증 의존성과 미들웨어에서).
- DB에 쓰기 직전(`before_flush`)에 대상 모델의 생성·수정·삭제를 모아 같은 트랜잭션에 `audit_logs` 행을 추가한다. **업무 데이터와 감사 로그가 함께 저장되거나 함께 취소**된다(요청이 실패하면 기록도 남지 않는다).
- 대상 모델과 기록할 필드를 한 곳(설정 표)에서 관리한다. 비밀번호 해시 같은 민감 필드는 값 대신 "변경됨"으로 남긴다.
- 서버 밖에서 실행한 스크립트(예: 잔액 정리 스크립트)는 사용자를 "시스템(스크립트 이름)"으로 기록한다.

## 5. 보는 방법

| 단계 | 내용 |
|---|---|
| 1차 | 관리자(대표) 전용 조회 API: 기간·대상·사용자로 검색 |
| 2차(선택) | 설정 메뉴에 "변경 이력" 화면, 거래처 상세에 "잔액 변경 이력" 버튼. **화면 추가라 따로 승인** |

감사 로그는 **수정·삭제 API를 만들지 않는다**(기록의 신뢰성). 오래된 기록 정리는 필요해지면 그때 정한다(기본: 보관 기간 제한 없음).

## 6. 위험과 대응

| 위험 | 대응 |
|---|---|
| 기록 실패가 업무 요청까지 실패시킴 | 같은 트랜잭션이라 함께 실패한다. 기록 코드는 단순하게 유지하고 테스트로 대상 모델 전체를 덮는다 |
| 기록이 너무 많거나 쓸모없는 변경까지 남음 | 대상 모델·필드를 화이트리스트로 관리(2장 범위만) |
| 개인정보·비밀정보 저장 | 비밀번호 해시·토큰은 저장하지 않음. 계좌번호는 기록하되 관리자만 조회 |
| 성능 | 쓰기 요청마다 행 1~3개 추가 수준. 5인 규모에서 체감 없음 |
| 테스트 데이터베이스 | 테스트 DB도 리비전으로 만들어지므로 자동 반영. 기록 내용 검증 테스트 추가 |

## 7. 진행 단계 (승인 후, 단계마다 테스트 + 커밋)

| 단계 | 작업 | DB 변경 |
|---|---|---|
| 1 | `AuditLog` 모델 + 리비전 `0003_audit_logs` (테스트 DB 에만 적용해 검증) | 테스트 DB |
| 2 | 요청 정보 전달(`contextvars`) + 자동 기록(`before_flush`), 대상: 매입매출·입출금·거래처 | 없음 |
| 3 | 직원 계정·문서 상태 + 로그인 이벤트 | 없음 |
| 4 | 관리자 조회 API | 없음 |
| 5 | **개발 DB 백업 후 `alembic upgrade head`** | 개발 DB 에 테이블 1개 **[승인]** |
| 6(선택) | 조회 화면 | 화면 추가 **[승인]** |

예상 규모: 1~4단계 반나절~하루.

## 8. 결정이 필요한 것

1. 2장의 기록 범위(돈·권한·삭제·로그인)가 적절한지, 더하거나 뺄 것이 있는지
2. 기록 방식 B(자동 감지) 제안에 동의하는지
3. 1~4단계를 진행한 뒤, 개발 DB 적용(5단계)과 조회 화면(6단계)은 따로 승인받는 방식이 좋은지
