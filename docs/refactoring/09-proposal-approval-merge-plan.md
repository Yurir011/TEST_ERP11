# 09. 품의서 결재 단계 테이블 통합 계획 (승인 대기)

> 작성일: 2026-10-16 · 관련: [05-remaining-issues.md](05-remaining-issues.md) S1·S2
> **이 문서는 계획이다. 승인 전에는 코드·DB를 바꾸지 않는다.** 이번 조사도 DB를 읽기만 했다.

## 1. 현재 상태

결재 단계(누가 몇 번째로 결재하고, 승인·반려했는지)를 두 곳에 나눠 저장한다.

| 문서 | 저장 테이블 | 처리 코드 |
|---|---|---|
| 연차, 증명서, 견적서·거래명세서·세금계산서·발주서 | 공용 `approval_steps` (대상 종류 + 대상 번호) | `core/approval.py` 공통 함수 사용 |
| **품의서** | 전용 `proposal_approval_steps` | `routers/proposals.py`가 자체 구현 |

두 테이블의 컬럼(단계 순서, 직책, 결재자, 상태, 결정 시각)과 상태 값(`pending`/`approved`/`rejected`)은 **사실상 같다.** 품의서만 따로 있어서 결재 규칙을 바꿀 때 두 군데를 고쳐야 하고, 품의서는 앞서 만든 결재 공통 함수(`approve_current_step` 등)의 혜택을 받지 못한다.

### 개발 DB (읽기 전용 조사)
| 항목 | 값 |
|---|---|
| 품의서 | 9건 |
| 품의서 결재 단계(`proposal_approval_steps`) | 9행 (승인 7, 반려 2) |
| 공용 결재 단계(`approval_steps`) | 44행 (연차 4, 증명서 21, 문서 19) |

### 영향받는 코드
`routers/proposals.py`(16곳), `routers/notifications.py`(결재 완료 표시 1곳), `services/proposal_pdf.py`(직인 표 1곳), `schemas/proposal.py`, `models/proposal.py`. 프론트엔드는 **바꿀 필요가 없다**(API 응답 모양을 그대로 유지한다).

## 2. 목표 상태

- 품의서 결재 단계도 공용 `approval_steps`에 대상 종류 `proposal`로 저장한다.
- 품의서 결재도 `core/approval.py`의 공통 함수(결재선 검증, 단계 생성, 자기결재 진행, 승인·반려 진행)를 쓴다.
- **API 응답(품의서의 `steps` 목록 모양, 상태 값)과 화면은 그대로.** 결재 규칙(전결, 자기결재, 삭제 결재, 반려 시 복원)도 그대로.

## 3. 데이터 옮기기 (Alembic 리비전 2개)

| 리비전 | 내용 |
|---|---|
| `0004_proposal_target_type` | enum `approvaltargettype`에 값 `proposal` 추가(`ALTER TYPE ... ADD VALUE IF NOT EXISTS`). PostgreSQL 제약으로 별도 리비전·자동 커밋 구간에서 실행 |
| `0005_move_proposal_steps` | `proposal_approval_steps`의 모든 행을 `approval_steps`로 복사(대상 종류 `proposal`, 대상 번호 = 품의서 번호, 순서·직책·결재자·상태·결정 시각 그대로). 복사 전후 행 수와 상태별 수가 같은지 확인하고, 다르면 실패시켜 아무것도 바꾸지 않는다 |

- **옛 테이블은 바로 지우지 않는다.** 코드는 더 이상 쓰지 않지만 되돌릴 때를 위해 한동안 그대로 두고, 운영에서 문제없음을 확인한 뒤 별도 리비전 `0006`으로 지운다(그때 다시 승인).
- 되돌리기(downgrade): `approval_steps`에서 `proposal` 행을 지우면 원래 상태가 된다(옛 테이블이 남아 있으므로).
- 적용 전 `pg_dump` 백업(07 문서 절차).

## 4. 코드 변경

| 파일 | 변경 |
|---|---|
| `models/approval_step.py` | `ApprovalTargetType.proposal` 추가 |
| `models/proposal.py` | `Proposal.steps` 관계 제거(옛 모델 클래스는 테이블이 남아 있는 동안 유지하되 코드에서 쓰지 않음) |
| `routers/proposals.py` | 단계 조회·생성·승인·반려·삭제 결재를 `core/approval.py` 함수로 교체. 품의서를 지울 때 `approval_steps`의 해당 행도 지운다(지금은 FK의 CASCADE 가 자동으로 지움 → 공용 테이블은 FK 가 없으므로 직접 지워야 함) |
| `routers/notifications.py` | "내가 결재한 품의서" 표시를 공용 테이블 조회로 |
| `services/proposal_pdf.py` | 직인 표가 단계 목록을 인자로 받도록 |
| `schemas/proposal.py` | 단계 상태 타입을 공용 `ApprovalStepStatus`로(값이 같아 응답은 동일) |

`proposals.py` 분할(647줄 → 목록·작성/수정·결재·첨부·파일)은 통합이 끝나고 안정된 뒤 `project_documents`와 같은 방법(안전망 테스트 → 그대로 이동 → AST 비교)으로 따로 진행한다.

## 5. 안전망 (코드 변경 전에 먼저)

품의서 결재는 아직 자동 테스트가 없다. 통합 전에 아래를 테스트로 고정한다.

1. 2단계 결재: 승인 → 다음 결재자 → 최종 승인, 지정되지 않은 사람 거절
2. 반려: 단계 상태·반려 사유, 이후 승인 불가
3. 전결, 자기결재(기안자가 결재선에 포함)
4. 삭제 결재: 최종 승인 시 품의서 삭제, 반려 시 결재선 포함 승인 상태 복원
5. 목록의 "내 결재함"(`approver_mine`), 대시보드 업무 알림의 "결재완료" 표시
6. 응답의 `steps` 모양(순서·직책·결재자 이름·상태·결정 시각)
7. 품의서 삭제 시 결재 단계도 함께 사라짐

같은 테스트가 **통합 전과 후에 모두 통과**해야 한다.

## 6. 진행 단계

| 단계 | 작업 | DB 변경 |
|---|---|---|
| 1 | 안전망 테스트 추가(5장) | 없음 |
| 2 | 리비전 0004·0005 작성, 테스트 DB 에서 검증(옛 테이블에 데이터를 넣고 옮겨지는지 확인하는 테스트 포함) | 테스트 DB |
| 3 | 코드 교체(4장), 안전망 테스트 통과 확인 | 없음 |
| 4 | **개발 DB 백업 → `alembic upgrade head` → 행 수 비교(9행)** | 개발 DB **[승인]** |
| 5 | (나중에) 옛 테이블 삭제 리비전 0006 | **[승인]** |

중간에 테스트가 실패하면 그 단계에서 멈추고 보고한다.

## 7. 위험과 대응

| 위험 | 대응 |
|---|---|
| 옮기는 중 데이터 누락 | 리비전 안에서 행 수·상태별 수 비교, 다르면 실패(트랜잭션 취소) |
| 품의서 삭제 시 결재 단계가 남음(공용 테이블은 FK 없음) | 삭제 코드에서 직접 지우고, 테스트 7번으로 확인 |
| 대시보드 "결재완료" 표시가 사라짐 | 테스트 5번 |
| 코드 배포와 DB 적용 순서가 어긋남 | 서버 시작 시 리비전 확인(07 문서)으로 최신이 아니면 경고/거부 |
| 되돌려야 할 때 | 옛 테이블이 남아 있으므로 downgrade + 이전 커밋으로 복구 |

## 8. 승인 요청

1. 이 방식(공용 테이블로 복사, 옛 테이블은 당분간 보존)으로 진행해도 되는지
2. 1~3단계(개발 DB 변경 없음)를 먼저 하고, 개발 DB 적용(4단계)은 결과를 본 뒤 따로 승인받는 방식이 좋은지
