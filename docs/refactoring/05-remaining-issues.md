# 05. 미해결 문제와 향후 개선 사항

> 리팩토링 진행 중 발견했지만 이번 단계에서 고치지 않은 항목을 모은다. 진행하면서 갱신한다.

## 데이터·금액

| # | 내용 | 비고 |
|---|---|---|
| R1 | **거래처 잔액 정리 필요**: 부분 결제 기능 이전에 입력한 "잔액만 줄이는" 출금/입금 때문에 일부 거래처(델타 통신, 크레신)의 DB 잔액이 0원이고, 미결제 건의 남은 금액과 다르다. 입출금관리 화면은 건 기준으로 계산해 맞게 보이지만 잔액을 직접 읽는 화면은 0원으로 보인다. | 테스트 입력이었는지 사용자 확인 후 일회성 정리. 데이터 변경이라 승인 필요 |
| R2 | **잔액 정산의 비대칭**: 잔액보다 많이 차감하면 0에서 멈추는데(`apply_balance_settlement`), 되돌릴 때는 입력 금액 전체를 더한다. 차감 때 잘려 나간 만큼 복원값이 과대가 된다(예: 잔액 300에서 500 차감 → 0, 되돌리면 500). | 동작을 테스트로 고정해 둠. 수정은 업무 규칙 결정 후 |
| R3 | `sales_documents.py`는 품목별 반올림 없이 합계를 곱해 부가세를 계산한다(다른 문서는 품목별 반올림 후 합산). | 통일 여부 결정 필요 |
| R4 | 외화(달러·엔) 거래: 매입매출·입출금은 원화만 지원한다. 문서(견적서 등)만 통화를 가진다. | 기능 개발 항목(리팩토링 범위 밖) |
| R5 | 부분 결제가 있는 매입매출 건을 삭제한 뒤 그 입출금을 따로 삭제하면 거래처 잔액이 늘어날 수 있다(연결이 끊긴 결제가 잔액만 줄이는 결제로 취급됨). | 삭제 흐름 정리 시 함께 처리 |

## 구조·품질

| # | 내용 | 계획 단계 |
|---|---|---|
| S1 | 결재 단계 처리는 3개 도메인에서 공통화했다(P3-2). **품의서만 별도 단계 테이블**(`ProposalApprovalStep`)을 써서 남아 있다. 통합하려면 스키마·데이터 이전이 필요 | 승인 필요 |
| S2 | `project_documents.py`(1,155줄), `proposals.py`(647줄) 분할 | P3 (착수 전 별도 확인) |
| S3 | 프론트엔드 거대 페이지 5개 분해, 승인/반려 핸들러 중복 | P4 |
| S4 | 이펙트 안 setState 9곳(린트 경고) | P4 |
| S5 | 프론트엔드 번들 단일 파일 1,002KB | 측정 후 코드 분할 검토 |
| S6 | 프론트엔드 순수 함수 테스트는 vitest 로 도입(P4-3). 화면(컴포넌트) 테스트는 DOM 환경 도입이 필요해 미도입 | 필요 시 별도 검토 |
| S7 | `npm audit` 고위험 1건: `source-map-js`(빌드 도구 전이 의존성). `npm audit fix`로 해결 가능해 보이나 락파일이 바뀌므로 별도 승인 후 진행 | 낮음 |

## 보안·운영 (승인 후 진행)

JWT 비밀키 기본값 방지, `LOG_LEVEL` 기본값, 로그인 제한, CORS, 업로드 내용 검사, 감사 로그, 마이그레이션 체계(Alembic)는 [02-plan.md](02-plan.md) P5·P6 참고.

## 미검증

- 팝빌·홈택스·OCR 연동 동작, PDF·엑셀 생성 결과, 정기 이체 생성은 자동 테스트가 없다.
- 브라우저 화면 동작은 자동으로 검증하지 못한다.
