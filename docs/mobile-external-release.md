# 모바일 외부 공개 준비 (패스키 포함)

> 사내망 밖의 직원 폰에서 ERP 모바일 화면(`/m`)을 쓰기 위한 준비 목록이다. 코드는 준비되어 있고, 아래 **서버·네트워크 작업은 운영 서버에서 해야 한다**(이 저장소에는 운영 서버 설정이 없어 확인하지 못한 부분이 있다).

## 1. 왜 HTTPS와 도메인이 먼저인가
- 패스키(지문·얼굴 로그인)는 **HTTPS에서만** 동작하고(개발 PC의 `localhost`만 예외), **도메인에 묶인다.**
- 지금 직원 앱의 서버 주소는 `http://www.epik.bio:3102`(HTTP)다. 이 주소로는 패스키를 쓸 수 없다.
- 도메인을 나중에 바꾸면 직원이 패스키를 **다시 등록**해야 하므로, 쓸 도메인을 먼저 정한다. 가능하면 `www.` 같은 하위 주소가 아니라 상위 도메인(예: `epik.bio`)을 `WEBAUTHN_RP_ID` 로 정한다.

## 2. 서버 설정 (`backend/.env`)
```
ENVIRONMENT=production
JWT_SECRET_KEY=<48자 이상의 무작위 값>        # 기본값이면 production 에서 서버가 시작되지 않는다
LOG_LEVEL=INFO
WEBAUTHN_RP_ID=epik.bio                       # 사이트 도메인 (포트·https:// 없이)
WEBAUTHN_ORIGINS=["https://www.epik.bio"]     # 브라우저 주소창에 보이는 주소 (JSON 배열)
# WEBAUTHN_RP_NAME=BENCH ERP                  # 기기 안내창에 보이는 이름 (기본값 그대로 두어도 된다)
```
- `WEBAUTHN_RP_ID` 또는 `WEBAUTHN_ORIGINS` 가 비어 있으면 패스키 기능은 꺼진 상태다. 로그인 화면에 [지문·얼굴로 로그인] 버튼이 나오지 않고, 비밀번호 로그인은 그대로 된다.
- 확인: `https://도메인/api/passkeys/status` → `{"enabled": true}`

## 3. DB 갱신 (서버에 올릴 때)
1. DB 백업: 프로젝트 루트의 `backup.bat`
2. `cd backend && venv\Scripts\python.exe -m alembic upgrade head`
   - `0026_withdrawn_status` : 연차·증명서·품의서 상태에 "회수됨" 추가
   - `0027_passkey_credentials` : 패스키 저장 표 추가 (기존 표는 바꾸지 않음)
3. 패키지: `venv\Scripts\python.exe -m pip install -r requirements.txt` (`webauthn` 과 의존 패키지가 추가됨)

## 4. HTTPS 문지기(리버스 프록시)
인증서 발급·갱신을 자동으로 해 주는 **Caddy** 를 서버 PC 에 설치해 앞에 둔다. 설정 파일은 [`deploy/Caddyfile`](../deploy/Caddyfile), 실행 파일은 [`deploy/start-caddy.bat`](../deploy/start-caddy.bat), **단계별 설치 안내는 [`docs/server-https-setup.md`](server-https-setup.md)** 에 있다.
- 쓸 주소는 지금 서버 주소에 이미 쓰고 있는 `www.epik.bio` 를 그대로 쓴다(도메인 DNS 를 바꿀 필요가 없다). 새 하위 주소(`erp.epik.bio` 등)를 쓰려면 DNS 관리 권한이 필요하다.
- 공유기에서 **80, 443 포트**를 서버 PC 로 추가로 열고(지금 열려 있는 3102 는 그대로 둔다), 서버 PC 의 내부 포트는 외부에 직접 열지 않는다.
- 예전 주소 `http://www.epik.bio:3102` 는 그대로 동작하므로 직원 PC 앱은 바로 바꾸지 않아도 된다. HSTS 는 켜지 않는다(예전 주소가 끊길 수 있다).

### 접속자 IP 전달 (이미 반영됨, 서버 재시작 필요)
프록시나 화면 서버(Vite)를 거치면 백엔드는 접속자를 **중간 서버의 주소(127.0.0.1)**로 본다. 그대로 두면 로그인 실패 제한(IP 기준)이 직원 전체에 한꺼번에 걸려, 한 사람이 틀리면 모두 잠길 수 있고 감사 로그의 접속 주소도 전부 같아진다.
- 백엔드(uvicorn)는 기본값으로 `127.0.0.1` 에서 온 `X-Forwarded-For` 를 믿는다. 그래서 Caddy 가 같은 PC 에 있으면 uvicorn 옵션을 따로 줄 필요가 없다.
- 운영 서버(포트 3102)는 **nginx 가 빌드된 화면을 내보내고 `/api` 를 백엔드로 넘기는 구조**로 보인다(2026-11-04, 응답 헤더 `nginx/1.30.5`·`V.0.72.036` 확인). 그 nginx 설정(`location /api` 부분)에 `proxy_set_header X-Forwarded-For $remote_addr;` 가 있는지 확인한다. 없으면 모든 접속이 nginx 주소로 보인다. 감사 로그(설정 → 감사 로그)의 접속 주소가 직원마다 다르게 찍히는지 보면 바로 알 수 있다.
- 개발 PC 의 화면 서버(Vite)는 `frontend/vite.config.ts` 의 `xfwd: true` 로 같은 일을 한다(개발용이며 운영과는 무관하다).
- 프록시가 다른 PC 에 있으면 uvicorn 을 `--forwarded-allow-ips="프록시 주소"` 로 시작한다. 모든 주소(`*`)를 허용하지 않는다(접속자가 주소를 속일 수 있다).

## 5. 직원 사용 순서
1. 직원이 폰 브라우저로 `https://도메인` 에 접속해 **비밀번호로 로그인**한다.
2. 모바일 화면 위쪽의 **내 정보**(사람 아이콘) → "이 폰에 패스키 추가" → 지문·얼굴 확인.
3. 다음부터 로그인 화면의 **[지문·얼굴로 로그인]** 을 누른다. 한 직원이 기기마다 최대 5개까지 등록할 수 있다.
4. 폰 화면에 추가(PWA)하는 작업은 이후 단계에서 한다.

## 6. 폰을 잃어버렸을 때
1. 관리자가 **설정 → 직원 → 해당 직원 수정 화면 → "패스키"** 칸에서 그 기기를 삭제한다. 삭제하면 그 폰으로는 패스키 로그인이 되지 않는다.
2. 이미 받아 둔 로그인 토큰은 만료(기본 12시간)될 때까지 유효하다. 급하면 해당 직원의 **비밀번호를 바꾸고**, 필요하면 계정을 잠시 비활성화한다(비활성 계정은 토큰도 바로 막힌다).
3. 감사 로그에서 `login_success`/`login_failed`(패스키 포함)를 확인한다.

## 7. 알아 둘 한계
- 로그인 실패 제한과 패스키 확인값은 **서버 프로세스 메모리**에만 있다. 서버를 재시작하면 초기화되고, 서버를 여러 프로세스로 띄우면 각각 따로 센다. 지금처럼 프로세스 하나로 운영하는 것을 전제로 한다.
- 기기에 따라 패스키 서명 횟수가 항상 0 으로 오는 경우가 있다(iCloud 키체인 등). 서버는 이를 정상으로 받아들이고, 횟수가 오르던 기기가 거꾸로 가면 복제로 보고 거절한다.
- 다음 단계(매출매입·통계)를 열기 전에 **민감 화면 진입 시 패스키 재확인**을 넣을 예정이다.

## 8. 점검 목록
- [ ] 도메인이 공인 IP 를 가리키고 `https://도메인` 이 열린다 (인증서 경고 없음)
- [ ] 외부에서 3102·8000 등 내부 포트로 직접 접속되지 않는다
- [ ] 화면 서버를 다시 시작한 뒤, 감사 로그의 접속 주소가 `127.0.0.1` 이 아닌 실제 주소로 찍힌다
- [ ] `.env` 의 `ENVIRONMENT=production`, `JWT_SECRET_KEY`, `WEBAUTHN_*` 설정
- [ ] DB 백업 후 `alembic upgrade head` (현재 `0027_passkey_credentials`)
- [ ] `/api/passkeys/status` 가 `{"enabled": true}`
- [ ] 직원 1명으로 패스키 등록 → 로그아웃 → 패스키 로그인 확인
- [ ] 관리자가 그 직원의 패스키를 삭제하면 패스키 로그인이 막히는지 확인
